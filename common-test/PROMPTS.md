## 0. 공통 테스트를 만들 때 쓴 프롬프트 (종휘)

> 이 프롬프트 + 과제 Phase 1 요구사항을 Claude 에 넣어 만들었다.
> 그 뒤 "종휘 구현에 유리한 곳이 없는지 확인해 줘" 로 한 번 더 점검했다 (REVIEW.md 1-1장).

```
미니 React Phase 1 공통 테스트 생성
역할
당신은 소프트웨어 테스트 엔지니어입니다.
현재 3명의 개발자가 AI 에이전트를 활용해 미니 React Phase 1을 각각 독립적으로 구현했습니다.
이번 작업의 목적은 3개의 구현을 공정하게 검증할 수 있는 공통 인수 테스트(Black-box Acceptance Test)를 작성하는 것입니다.
입력 자료

* 미니 React Phase 1 과제 요구사항 원문
* 프로젝트의 실행 환경 및 기술 제약

작업 지시
1. 요구사항 분석

* 과제 원문에서 검증 가능한 기능 요구사항을 추출하세요.
* 각 요구사항에 고유 ID를 부여하세요.
* 필수 요구사항과 선택적 품질 항목을 구분하세요.
* 명시되지 않은 기능을 임의로 필수 요구사항에 추가하지 마세요.

2. 공통 테스트 명세 작성
각 요구사항에 대한 테스트를 설계하세요.
각 테스트에는 다음 항목을 포함하세요.

* 테스트 ID
* 대응하는 요구사항 ID 및 원문 근거
* 테스트 목적
* 입력 및 실행 절차
* 기대 결과
* 실패 조건
* 정상 / 경계 / 예외 시나리오 분류

3. 테스트 구현

* 특정 팀원의 구현 코드를 참고하지 마세요.
* 외부에서 관찰 가능한 동작을 기준으로 테스트하세요.
* 내부 자료구조, 함수명, 특정 알고리즘에 종속되지 않도록 작성하세요.
* 공통 테스트 인터페이스를 정의하고, 필요한 경우 구현별 Adapter를 연결할 수 있도록 설계하세요.
* Adapter에는 테스트 대상의 기능을 대신 수행하는 로직이 들어가면 안 됩니다.
* 실제 실행 가능한 테스트 코드를 작성하세요.

4. 자체 검토

* 요구사항 누락 여부
* 잘못된 Assertion 여부
* 불필요하게 엄격한 검증 조건
* 테스트 간 상태 간섭 여부
* 정상 구현이 실패할 수 있는 조건
* 결함 구현이 잘못 통과할 수 있는 조건

위 항목을 검토하세요.
제약 사항

* 특정 구현에 유리한 테스트를 작성하지 마세요.
* 기존 구현 코드를 수정하지 마세요.
* 과제 원문이 불명확한 경우 임의로 해석하지 말고 '판단 필요'로 분류하세요.
* 테스트를 실행하지 않았다면 통과했다고 주장하지 마세요.
* 테스트 코드가 실제 구현에 연결되기 전이라면 실행 가능 여부와 미검증 범위를 명확히 표시하세요.

최종 산출물

1. 요구사항-테스트 매핑표
2. 공통 테스트 명세
3. 공통 테스트 코드 및 실행 방법
4. Adapter 인터페이스 명세
5. 자체 검토 보고서
6. 미검증 사항 및 잔여 위험

최종 목표: 서로 다른 세 구현에 동일하게 적용할 수 있는 공정하고 재현 가능한 테스트 체계를 구성하는 것입니다.
```

## 1. 내 구현을 연결하고 돌리기 (모두)

```
너는 내 미니 React Phase 1 구현을 팀 공통 테스트에 연결하는 역할이다.

자료
- 공통 테스트 폴더 : <압축 푼 경로>/mini-react-common-test
- 내 구현 폴더 : <내 구현 경로>

할 일
1. 공통 테스트 폴더의 README.md 와 ADAPTER.md 를 먼저 읽는다.
2. adapters/template.js 를 복사해 adapters/<내 이름>.js 를 만든다.
   - 내 구현의 함수를 "부르기만" 한다. 비교 · patch · 변환 로직을 Adapter 에 쓰지 않는다.
   - 내 구현이 ES 모듈이거나 번들러를 쓰면 ADAPTER.md 의 loadModules 예시와 page.open 을 따른다.
3. 공통 테스트 폴더에서 npm install 뒤 ADAPTER=adapters/<내 이름>.js npm test 를 실행한다.
4. 아래 형식으로 보고한다.

지키는 것
- tests/ 와 lib/ 의 파일은 고치지 않는다. 테스트가 틀렸다고 보이면 고치지 말고 보고에 적는다.
- 내 구현 코드도 지금은 고치지 않는다. 실패는 보고만 한다.
- 실행하지 못한 테스트를 통과했다고 말하지 않는다.

보고 형식
1. 결과 한 줄 : tests / pass / fail / todo 숫자 (npm test 마지막 줄 그대로)
2. 실패한 테스트 표 : 테스트 ID | 기대 | 실제 | 원인 분류
   - 원인 분류 : 내 구현 결함 / 테스트 문제 / Adapter 문제 / 판단 필요(J1~J6 중 무엇)
3. todo(선택) 테스트 중 실패한 것 : ID 만
4. Adapter 파일 전문 (다른 사람이 "로직을 대신 하지 않았는지" 확인할 수 있게)
5. 연결하면서 막힌 점 (예 : jsdom 이 페이지를 못 엶)
```

### 2-A. 요구사항 정합성 (종휘)

```
# 공통 테스트 독립 검증 A — 요구사항 정합성

당신은 요구사항 기반 테스트 검증 담당자입니다.

## 검증 목적

공통 테스트가 미니 React Phase 1 과제의 요구사항을 정확하고 빠짐없이 반영하는지 검증하세요.

## 검증 항목

1. **요구사항 누락**
    
    - 과제의 모든 필수 기능이 테스트로 검증되는가?
        
    - 테스트되지 않는 요구사항은 무엇인가?
        
2. **과도한 요구사항**
    
    - 과제에 없는 기능을 필수 테스트로 강제하는가?
        
    - 특정 구현 방식이나 자료구조를 요구하는가?
        
    - 특히 작성자(종휘) 구현에 유리한 조건이 있는가? (REVIEW.md 1-1장 이후에도 남은 것)
        
3. **요구사항 해석**
    
    - 테스트의 기대 동작이 원문과 일치하는가?
        
    - 요구사항이 모호한데 임의로 가정한 부분이 있는가?
        
    - SPEC.md 의 판단 필요 J1~J6 을 먼저 보고, 그 밖에 빠진 모호한 곳을 찾는다.
        
4. **테스트 커버리지**
    
    - 정상·경계·예외 조건이 적절하게 포함되어 있는가?
        
    - 중요도에 비해 불필요하거나 중복된 테스트는 없는가?
        

## 제약

- 기존 구현 코드를 평가 근거로 사용하지 마세요.
    
- 테스트 원본을 수정하지 마세요.
    
- 모든 지적 사항에 요구사항 원문과 테스트 ID를 근거로 제시하세요.
    
- 단순히 테스트 개수가 많다는 이유로 높은 품질을 판정하지 마세요.
    

## 출력

- 요구사항-테스트 매핑표
    
- 누락된 요구사항
    
- 과도하거나 모호한 테스트
    
- 수정 권고사항
    
- 최종 판정: 적합 / 수정 필요 / 판단 보류
```

### 2-B. 검사 방식의 정확성 (정혁)

```
# 공통 테스트 독립 검증 B — Assertion 정확성

당신은 테스트 코드의 정확성과 신뢰성을 검증하는 QA 엔지니어입니다.

## 검증 목적

테스트가 올바른 입력과 기대 결과를 사용하며, 실제 결함을 정확하게 탐지하도록 작성되었는지 확인하세요.

## 검증 항목

1. **Assertion 정확성**
    
    - 각 테스트의 기대 결과가 요구사항에 부합하는가?
        
    - 실제 동작을 검증하는 Assertion이 존재하는가?
        
    - 테스트가 실행만 되고 검증 없이 통과하는 경우가 있는가?
        
2. **거짓 양성 및 거짓 음성**
    
    - 잘못된 구현이 통과할 가능성이 있는가?
        
    - 정상 구현이 부당하게 실패할 가능성이 있는가?
        
3. **테스트 독립성**
    
    - 테스트 실행 순서에 따라 결과가 달라질 수 있는가?
        
    - 전역 상태, DOM, 이벤트 리스너 등의 정리가 충분한가?
        
    - 비동기 작업이나 실행 환경 차이로 불안정해질 가능성이 있는가?
        
4. **Adapter 검증**
    
    - Adapter가 구현 차이만 연결하는가?
        
    - 실제 테스트 대상의 기능을 대신 구현하거나 결과를 보정하지 않는가?
        
    - 지금 있는 Adapter(template.js · jonghwi.js)만 보고, 아직 없는 팀원 Adapter 는 미검증으로 적는다.
        

## 제약

- 특정 팀원의 구현 코드를 평가 근거로 사용하지 마세요.
    
- 테스트 원본을 수정하지 마세요.
    
- 실제 코드의 파일 경로와 Assertion을 근거로 제시하세요.
    
- 실행하지 않은 검증은 미검증으로 명시하세요.
    

## 출력

- 테스트별 적합 / 수정 필요 / 판단 보류
    
- 잘못되거나 누락된 Assertion
    
- 불안정하거나 구현에 종속적인 테스트
    
- 수정 권고사항 및 근거
    
- 최종 판정
```

### 2-C. 결함 탐지 능력 (민기)

```
# 공통 테스트 독립 검증 C — Mutation Testing

당신은 소프트웨어 테스트의 결함 탐지 능력을 검증하는 엔지니어입니다.

## 검증 목적

공통 테스트가 실제로 주요 기능 결함을 탐지할 수 있는지 확인하세요.

## 작업 지시

### 1. 대표 결함 시나리오 선정

과제 요구사항을 기반으로 주요 기능별 결함 시나리오를 도출하세요.

예시:

- Virtual DOM 생성 시 자식 노드 누락
    
- Diff 수행 시 텍스트 변경 무시
    
- 속성 변경 또는 삭제 처리 누락
    
- Patch 적용 시 기존 DOM이 갱신되지 않음
    

단, 실제 과제에 해당하는 기능만 사용하세요.

REVIEW.md 2장의 결함 구현 9개(통째로 다시 그리기 · 지우기 / 속성 / 글자 빠뜨림 · XSS · 기록 안 함 · 테스트 영역 안 바꿈 등)와 겹치지 않는 결함을 고르세요.

### 2. 결함 주입

- 테스트 대상의 격리된 복사본에 대표 결함을 주입하세요.
    
- 정상 동작하는 기준 구현 또는 최소 검증용 구현이 필요하다면 준비하세요.
    
- 기준 구현은 내 구현의 복사본을 쓰고, 내 Adapter 로 연결하세요. (selfcheck/run.sh 는 종휘 구현이 있어야 돌아갑니다.)
    
- 결함은 한 번에 하나씩 주입하세요.
    
- 원본 테스트와 팀원 구현 코드를 수정하지 마세요.
    

### 3. 테스트 실행

- 정상 구현이 해당 테스트를 통과하는지 확인하세요.
    
- 결함을 주입한 구현에서 해당 테스트가 실패하는지 확인하세요.
    
- 실제로 실행한 명령과 결과를 기록하세요.
    

### 4. 결과 분석

- 결함을 탐지한 테스트를 식별하세요.
    
- 탐지하지 못한 결함을 기록하세요.
    
- 테스트 자체의 문제인지, 주입한 결함이 무효한 것인지 구분하세요.
    
- 실행할 수 없는 항목은 미검증으로 표시하세요.
    

## 제약

- 테스트 자체의 Assertion을 수정하지 마세요.
    
- 반드시 격리된 복사본에서 작업하세요.
    
- 테스트를 실행하지 않았다면 탐지 성공을 주장하지 마세요.
    
- 대표 결함 탐지는 전체 테스트의 완전성을 보장하지 않는다는 점을 명시하세요.
    

## 출력

- 결함 주입 시나리오 목록
    
- 정상 구현 실행 결과
    
- 결함 주입 후 실행 결과
    
- 탐지 성공 / 탐지 실패 / 미검증
```
